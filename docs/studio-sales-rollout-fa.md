# پنل فروش زاد — انتشار ۲۰۲۶/۱۰/۰۵

## مبنا و محدوده

این پچ مکمل نسخهٔ manager-mobile پس از اصلاح لینک محصول ناقص و ورود پاییزی است.
مبنای اعلام‌شدهٔ لوکال: `3706c39` روی `feature/manager-mobile`.
کد مبنا از snapshot موجود و تغییرات تأییدشدهٔ گفتگو ساخته شده است؛ دسترسی زنده به VPS نداشته‌ایم.
تاریخچهٔ Git لوکال و VPS متفاوت است؛ پذیرش پچ و بررسی فایل‌ها معیار اولیهٔ سازگاری است.
پچ شامل هیچ دیتابیس، مدیا، فایل محیطی، اطلاعات محرمانه یا patch قدیمی نیست.

## قابلیت‌ها

- پنل مستقل `/sales/` با جست‌وجوی فاکتور/فلوریست، ویترین تصویری، موجودها، فروش امروز، همه، سفارشی‌ها و کشیده‌شده‌ها.
- جزئیات محصول، ویرایش تصویر، قیمت، فاکتور، فلوریست، نوع محصول و یادداشت.
- ثبت فروش، ثبت کشیده‌شدن و بازگشت محصول روزانه به موجودی با علت اجباری و تأیید.
- فرم قدیمی نمی‌تواند دادهٔ تازه را بازنویسی کند؛ نسخهٔ محصول در تراکنش بررسی می‌شود.
- ورود کاربرِ دارای نقش فروش و بدون نقش مدیریت به `/sales/` هدایت می‌شود.
- نقش فروش مجوز مدیریت کاربران، تنظیمات تلگرام، ورود Django Admin یا حذف دائمی نمی‌دهد.
- تاریخچهٔ عملیات پنل فروش شامل حساب کاربر، زمان، دلیل، مقادیر قبلی و جدید است.
- مدیرِ دارای `view_studioproduct` می‌تواند `/sales/history/` را ببیند؛ ویرایش به نقش فروش نیاز دارد.
- حساب superuser به پنل فروش نیز دسترسی دارد.

## قواعد تجاری محفوظ

- محصولات سفارشی هنگام ثبت فروخته‌شده‌اند؛ پیامشان در گروه سفارشی حفظ می‌شود.
- بازگشت به موجودی فقط برای روزانه است. تبدیل نوع تولید بین روزانه/سفارشی در این نسخه نیست.
- ثبت فروش یا خروج روزانه فوراً موجودی سایت را می‌بندد؛ قاعدهٔ ۴۵ دقیقه‌ای خروج تلگرام حفظ می‌شود.
- در بازگشت، تاریخ فروش/خروج جاری پاک و سابقهٔ قبلی در audit نگهداری می‌شود.
- اگر پیام هنوز موجود باشد، همان پیام ویرایش می‌شود؛ اگر حذفش قطعی باشد، ارسال جدید در صف می‌رود.
- پاسخ‌های قدیمی پیش از بازگشت و پاسخ به پیام حذف‌شده نباید محصول بازگشته را دوباره بفروشند.
- ارسال نامشخص هرگز خودکار دوباره منتشر نمی‌شود؛ کاربر فروش باید تعیین تکلیف آن را به مدیر بسپارد.
- عملیات یک محصول با ارسال در حال انجام تداخل نمی‌کند؛ کاربر در صورت نیاز پیامِ تلاش مجدد می‌گیرد.
- پیام‌های قدیمی که مستقیماً کاربر در تلگرام فرستاده است ممکن است توسط بات قابل ویرایش نباشند؛ شکست همگام‌سازی در صف نشان داده می‌شود. این موارد نیازمند هماهنگی با مدیر هستند.
- قیمت نمایشی گزارش فعلی مانند قبل از قیمت جاری محصول محاسبه می‌شود؛ این بخش دفتر حسابداری یا گزارش گردش مالی/استرداد وجه نیست. audit مقادیر قبل/بعدِ اصلاح فروش را حفظ می‌کند.
- audit این نسخه مربوط به عملیات همین پنل است؛ تاریخچهٔ ناشناختهٔ قبل از نصب یا تمام ویرایش‌های خارج از پنل بازسازی نمی‌شود.
- اعلان خصوصی مدیر غیرفعال می‌ماند.

## تغییر تلگرام

Worker فقط یک envelope محدود جدید برای `editMessageMedia` دریافت می‌کند؛ مسیر، secret و envelope قبلی `sendPhoto` تغییر نمی‌کند.
به‌روزرسانی عکس و کپشن یک پیام موجود، عملیات idempotent است. ویرایشِ گم‌شده خودکار پیام دوم نمی‌سازد.
آدرس، token و شناسهٔ گروه‌ها تغییر نمی‌کنند.
برای انتشار این قابلیت باید **Worker جدید نیز deploy شود**. تعویض کد Django به‌تنهایی کافی نیست.
فایل مرجع بعد از اعمال پچ: `ops/cloudflare/zad-telegram-relay-worker.js`.

## آزمایش لوکال — ابتدا فقط این مرحله

در PowerShell، از ریشهٔ پروژه، ابتدا `git status --short` را ببینید؛ تغییرات کاری نامرتبط را وارد این commit نکنید.

```powershell
git switch -c feature/sales-workspace
git apply --check .\zad-sales-workspace.patch
git apply .\zad-sales-workspace.patch
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
node --test ops/cloudflare/zad-telegram-relay-worker.test.mjs ops/tests/studio-actions.test.cjs
git diff --check
python manage.py migrate
python manage.py studio_account behnaz --sales
python manage.py runserver
```

برای حساب تازه، رمز در prompt امن پرسیده می‌شود؛ برای حساب موجود بدون `--reset-password` رمز قبلی حفظ می‌شود.
دستور `--sales` تنها مجوز فروش را اضافه می‌کند و مجوزهای قدیمی حساب را حذف نمی‌کند.
نام `behnaz` صرفاً نمونه است؛ نام کاربری واقعی را انتخاب کنید.
از `/studio/login/` با حساب فروش وارد شوید یا با superuser مستقیماً `/sales/` را باز کنید.
در لوکال از دیتای آزمایشی و بدون token/relay زنده استفاده کنید. Worker پردازش صف را برای دیتای دمو اجرا نکنید.

## آزمون پذیرش قبل از VPS

1. روی گوشی واقعی: موجودها → فاکتور → فروش؛ علت و تأیید الزامی باشند.
2. لغو فروش پیش از خروج پیام: یک محصول موجود در سایت و یک پیام در گروه باقی بماند.
3. لغو فروش بعد از خروج قطعی پیام: تنها یک انتشار جدید انجام شود؛ پاسخ به پیام قبلی بی‌اثر باشد.
4. فروش مجدد: تاریخ جدید در آمار قرار گیرد و پیام جدید بعد از مهلت خروج حذف شود.
5. تغییر قیمت/تصویر: محصول در سایت اصلاح و پیام همان محصول در گروه به‌روز شود.
6. دو تب روی یک محصول: ذخیرهٔ تب قدیمی رد شود.
7. سفارش اختصاصی: موجودی عمومی نسازد و پیامش حذف نشود.
8. حساب فروش: به صفحات کاربران/تنظیمات/ادمین دسترسی اضافه نداشته باشد.
9. مدیر: سابقهٔ مقدار قبلی، جدید، کاربر و دلیل اصلاح را ببیند.

## استقرار production — مرحلهٔ جدا، بعد از تأیید لوکال

این فایل مجوز اجرای خودکار روی VPS نیست و هیچ استقراری از طرف سازندهٔ پچ انجام نشده است.

1. commit و push فقط فایل‌های همین پچ. فایل‌های release و patchهای قبلی را با `git add .` وارد commit نکنید.
2. در PowerShell پچ release را با `git diff --binary --output=... BASE HEAD` بسازید؛ از `>` برای فایل patch استفاده نکنید.
3. SCP به `cloud-admin@2.144.24.150:/home/cloud-admin/`؛ روی VPS status و commit فعلی و `git apply --check` بررسی شود.
4. backup تازهٔ DB با pg_dump، کد و محیط اجرا؛ شاخهٔ deploy جدا و ثبت commit قبل از تغییر.
5. Worker جدیدِ بررسی‌شده را با همان secret/شناسه‌ها deploy کنید. این Worker با نسخهٔ قبلی Django سازگار است.
6. در بازهٔ کوتاه نگهداری، **هر دو سرویس** `zad.service` و `zad-studio-deliveries.service` متوقف شوند. Worker قدیمی Django نباید job نوع SYNC را بردارد.
7. پچ apply شود؛ check، makemigrations check و migrate plan اجرا شوند؛ سپس migration `0040` و collectstatic.
8. هر دو سرویس راه‌اندازی شوند؛ active بودن، صفحهٔ login و `studio_delivery_check` بررسی شود.
9. ابتدا با superuser روی یک محصول آزمایشی کنترل‌شده بررسی شود؛ سپس نقش فروش به حساب واقعی اضافه شود.
10. smoke test روی گوشی، کنترل صف و commit روی VPS. Worker شبکه به‌صورت mock تست شده است؛ یک smoke test واقعی لازم است.

## توقف و بازگشت

پس از ایجاد job نوع SYNC، بازگرداندن بی‌برنامهٔ worker قدیمی Django خطرناک است: نسخهٔ قدیمی ممکن است action جدید را خروج از گروه فرض کند.
در صورت مشکل، ابتدا worker صف متوقف شود. دسترسی فروش موقتاً غیرفعال و مشکل بررسی شود.
قبل از برگشت به کد قدیمی باید وضعیت تمام jobهای SYNC و ارسال‌های جاری تعیین تکلیف شود؛ jobها را کورکورانه حذف یا دوباره ارسال نکنید.
migration فقط فیلد nullable، جدول audit و choices اضافه می‌کند و داده‌های قبلی را بازنویسی نمی‌کند.
بازگردانی DB از backup پس از فعالیت واقعی کارکنان می‌تواند تغییرات جدید را از بین ببرد؛ rollback داده نباید خودکار باشد.

رفتار نقش‌ها، POST/CSRF، نسخهٔ قدیمی، audit، فروش مجدد، پیام قدیمی و چرخهٔ خروج بررسی شده‌اند.
