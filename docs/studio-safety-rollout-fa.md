# اصلاحات ایمنی Studio — ۱ اکتبر ۲۰۲۶

> راهنمای فعلی: [ادغام اصلاحات Studio](studio-reconciliation-rollout-fa.md).
> در نسخهٔ ادغام‌شده، اعلان خصوصی مدیر خاموش است و صف قدیمی بازیابی نمی‌شود.
> مراحل فعال‌سازی و بازیابی اعلان خصوصی در این سند، شرح نسخهٔ قبلی هستند و
> برای استقرار جدید اجرا نمی‌شوند.

این patch برای شاخهٔ `feature/studio-team-portal` و نسخهٔ مبنای
`6ad0f7d4b3f0f6a95f67ab7b67be541ea63d42d3` تهیه شده است.
بررسی و تست روی کپی مستقل پروژه با دیتابیس و رسانهٔ آزمایشی انجام شده است.
سرور عملیاتی، پیام‌های واقعی تلگرام و تنظیمات محیطی تغییر نکرده‌اند.

## تغییرات کاربردی

- ویرایش محصول مدیریتی، قیمت و عکس همان محصول را در دفتر استودیو و کاتالوگ
  عمومی هماهنگ می‌کند؛ ویرایش به‌تنهایی انتشار دوباره در گروه ایجاد نمی‌کند.
- ویرایش فقط فیلدهای تغییرکردهٔ فرم را ذخیره می‌کند. وضعیت تازهٔ محصول در
  دیتابیس دوباره بررسی می‌شود تا فرم بازمانده، فروش یا حذف جدید را برنگرداند.
- تغییر نوع تولیدِ رکورد ثبت‌شده و تغییر شمارهٔ فاکتورِ محصول دارای ارسال
  تلگرام مسدود است؛ این موارد نیازمند مسیر تبدیل مستقل هستند.
- تغییر قیمت یا وضعیت از مدیریت کاتالوگ، از جمله مدل واسط `SameDayFlower`،
  به دفتر و اعلان خصوصی منتقل می‌شود. مقدار ذخیره‌نشدهٔ یک فرم وارد اعلان نمی‌شود.
- محصول حذف‌شده از کارنامه، آمار و جزئیات قابل‌مشاهدهٔ فلوریست خارج می‌شود؛
  عکس، علت حذف و سابقهٔ مدیریتی نگه داشته می‌شوند.
- ریپلای یا ویرایش قدیمی تلگرام، محصول حذف‌شده را زنده نمی‌کند. اصلاح قیمت
  قدیمی‌تر، قیمت جدیدترِ ثبت‌شده از همان مسیر را برنمی‌گرداند.
- عکس خراب یا مفقود در صف اعلان خصوصی، به خطای قابل‌پیگیری تبدیل می‌شود و
  پردازش ارسال‌های گروه را متوقف نمی‌کند.
- اعلان‌های خصوصی هر محصول به ترتیب پردازش می‌شوند. نتیجهٔ نامشخص، بدون
  بررسی دستی دوباره ارسال نمی‌شود؛ توقف یا دیررسیدن پاسخ نیز مالکیت تلاش را حفظ می‌کند.
- صفحهٔ `/studio/admin-notifications/` برای پیگیری اعلان خصوصی اضافه شده است.
  دسترسی فلوریست به این صفحه مجاز نیست و اقدامات بازیابی در سابقهٔ مدیریت ثبت می‌شوند.
- تأیید حذف با JavaScript خارجی و سازگار با CSP انجام می‌شود؛ لغو، دلیل خالی،
  دوبارکلیک و جایگزینی جدول هنگام بازبودن تأیید پوشش داده شده‌اند.
- با بازکردن عملیات جدول روی موبایل، محتوای کمکی داخل همان ناحیهٔ اسکرول
  نگه داشته می‌شود تا صفحه و پنجرهٔ تأیید از عرض نمایشگر بیرون نروند.
- وابستگی موجودِ پردازش HEIF به `requirements.txt` اضافه شده است تا نصب تازه
  و CI با خطای `main.E102` متوقف نشوند.

فایل اجرایی `ops/cloudflare/zad-telegram-relay-worker.js` تغییر نکرده است.
این patch نیازمند جایگزینی Worker، تغییر شناسهٔ گروه‌ها یا ثبت دوبارهٔ webhook نیست.
مدل و migration تازه ندارد؛ فایل `.env`، دیتابیس و رسانهٔ عملیاتی جزو patch نیستند.

## بررسی روی local

فایل patch را در ریشهٔ پروژه قرار دهید. ابتدا وضعیت فعلی را ببینید:

```powershell
git status --short
git log -1 --oneline
git apply --check .\zad-studio-safety-6ad0f7d.patch
```

اگر فایل‌های پروژه تغییرات ثبت‌نشده دارند، ابتدا همان تغییرات را جداگانه حفظ کنید.
خود فایل دانلودشدهٔ patch می‌تواند untracked باشد. اگر بررسی اعمال patch خطا داد،
اعمال را ادامه ندهید؛ خروجی و تفاوت فایل‌های درگیر باید بررسی شوند. از `--reject`،
بازنویسی فایل‌های سرور با نسخهٔ local، یا reset اجباری استفاده نکنید.

پس از موفقیت بررسی، روی شاخهٔ مستقل اعمال و آزمایش کنید:

```powershell
git switch -c fix/studio-safety
git apply .\zad-studio-safety-6ad0f7d.patch
python -m pip install -r requirements.txt
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test --noinput
node --test ops/cloudflare/zad-telegram-relay-worker.test.mjs ops/tests/studio-actions.test.cjs
git diff --check
```

خروجی migration باید `No changes detected` باشد. ثبت محصول آزمایشی را روی local
انجام دهید؛ اجرای `seed_studio_demo`، `flush` یا واردکردن دیتابیس local روی VPS
بخشی از استقرار نیست.

## استقرار کنترل‌شدهٔ VPS

به‌دلیل تفاوت تاریخچهٔ Git و اصلاحات دستی قبلی سرور، موفقیت patch روی local
به‌تنهایی اثبات سازگاری با VPS نیست. پیش از هر تغییرِ سرور، از ریشهٔ پروژه فقط
وضعیت و بررسی سازگاری را اجرا کنید:

```bash
git status --short
git log -1 --oneline
git apply --check /home/cloud-admin/zad-studio-safety-6ad0f7d.patch
sudo systemctl is-active zad.service zad-studio-deliveries.service
```

در صورت ناسازگاری، اصلاحات موجود سرور باید حفظ و patch بر همان محتوا تطبیق داده
شود. به‌ویژه قالب حذف مدیریتیِ اصلاح‌شدهٔ قبلی را بدون بررسی بازنویسی نکنید.
قبل از استقرار، نسخهٔ کد قابل‌بازگشت را نگه دارید؛ استقرار کد نباید دیتابیس یا
رسانه را جایگزین یا بازگردانی کند.

اجرای نهایی را در یک زمان کوتاه و هماهنگ با تیم انجام دهید. هنگام توقف پردازشگر،
ارسال در حال اجرا ممکن است نتیجهٔ نامشخص داشته باشد؛ آن را خودکار به صف برنگردانید.
پس از اعمال سازگارِ کد، نصب وابستگی لازم، اجرای `check` و `collectstatic`، هر دو
سرویس `zad.service` و `zad-studio-deliveries.service` باید نسخهٔ جدید را بارگذاری
کنند. فقط restart وب‌سرویس، پردازشگر مقیم را به‌روز نمی‌کند.

این تغییر به تنظیم Nginx یا استقرار Worker نیاز ندارد. `migrate --plan` می‌تواند
برای اثبات نبودِ migration جدید اجرا شود؛ migration ناشناختهٔ نسخه‌ای دیگر را
همراه این patch اعمال نکنید.

## عیب‌یابی و بازیابی صف خصوصی

بررسی پیش‌فرض فقط تنظیم و شمارش صف‌ها را می‌خواند؛ هیچ درخواست شبکه‌ای ندارد:

```bash
/var/www/zad/venv/bin/python manage.py studio_delivery_check
```

برای خواندن هویت مقصد از تلگرام، بدون ارسال عکس یا تغییر صف:

```bash
/var/www/zad/venv/bin/python manage.py studio_delivery_check --network
/var/www/zad/venv/bin/python manage.py studio_delivery_check --network --destination admin
```

توکن یا relay secret در خروجی چاپ نمی‌شود. خطای `invalid_payload` در مقصد خصوصی
می‌تواند از ناسازگاری Worker فعال، آدرس relay یا تنظیم مقصد باشد؛ صرفاً با این
خطا نمی‌توان یکی از آن‌ها را علت قطعی دانست. نسخهٔ فعال را پیش از تغییر بررسی کنید.

در صفحهٔ پیگیری اعلان خصوصی:

- `FAILED` یا `RETRY`: پس از رفع علت، «تلاش دوباره» را بزنید. این اقدام صف را
  به‌روز می‌کند؛ ارسال واقعی را پردازشگر انجام می‌دهد.
- `UNCERTAIN`: نخست پیامِ همین فاکتور، قیمت و وضعیت را در گفت‌وگوی خصوصی پیدا
  کنید. اگر موجود است، شناسهٔ آن را با تأیید بررسی متصل کنید.
- اگر پیام واقعاً وجود ندارد، گزینهٔ تأیید نبودن پیام و ارسال دوباره را انتخاب
  کنید. تا پایان مهلت تلاش قبلی، درخواست پذیرفته نمی‌شود.
- اگر اعلان جدیدتری ارسال شده یا نتیجهٔ ارسال آن نامشخص است، پیام قدیمی را
  دوباره ارسال نکنید؛ صفحه این اقدام را مسدود می‌کند.

## شواهد و محدودیت بررسی

تست‌های Django، Worker و عملیات فرم، بررسی سیستم و نبود تغییر migration انجام
شده‌اند. مسیرهای ویرایش، مرتب‌سازی، تأیید و لغو حذف، پنهان‌شدن رکورد حذف‌شده از
پرتال و دسترسی صف خصوصی در Chromium و اندازه‌های دسکتاپ، تبلت و موبایل بررسی شدند.
محیط مرورگر سیاست CSP سخت‌گیرانه داشت و هیچ پردازشگر ارسال واقعی در آن اجرا نشد.

آزمایش backend روی SQLite مستقل انجام شده است؛ قفل‌گذاری PostgreSQL زیر بار واقعی
و ارسال زنده از تنظیمات VPS در این بررسی اجرا نشده‌اند. بررسی اولیهٔ صف‌ها و
سلامت هر دو سرویس بعد از استقرار همچنان لازم است. پیام‌های قبلاً نامشخص یا
failed به‌صورت دسته‌جمعی بازفرستاده نمی‌شوند.
