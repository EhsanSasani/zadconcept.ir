# راه‌اندازی Studio Operations

## دادهٔ نمایشی برای بازبینی ظاهر در لوکال

پس از اجرای migration روی دیتابیس لوکال، دستور زیر ۷۲ رکورد نمایشی در حدود دو ماه اخیر، دو فلوریست فعال، یک فلوریست غیرفعال، تصاویر گل موجود در پروژه و دو خطای نمونه برای صفحهٔ تنظیمات می‌سازد:

```bash
python manage.py seed_studio_demo
```

این دستور فقط با `DEBUG=True` و SQLite اجرا می‌شود. محصولات نمایشی فقط در دفتر استودیو هستند و به کاتالوگ سایت یا تلگرام وصل نمی‌شوند. اجرای دوباره رکورد تکراری نمی‌سازد. فاکتورها با `DEMO-ZAD-` آغاز می‌شوند؛ پس از بازبینی، همهٔ داده‌های نمایشی و تصاویر مربوط را با دستور زیر پاک کنید:

```bash
python manage.py seed_studio_demo --clear
```

برای حجم متفاوت داده از `--count 48` استفاده کنید (۱۲ تا ۱۲۰). رکوردهای واقعی و عکس‌های خارج از فضای demo حذف نمی‌شوند. فایل‌های تصویری داخل `MEDIA_ROOT/studio/demo-seed-v1/` ذخیره می‌شوند.

## اعمال پچ یکپارچه

این پچ نسبت به commit پایهٔ `d350f45` از شاخهٔ `main` ساخته شده است. در ریشهٔ مخزن، ابتدا `git status --short` را بررسی کنید؛ سپس فایل پچ را در یک مسیر خارج از مخزن قرار دهید و اجرا کنید:

```bash
git apply --check /path/to/zad-studio-operations.patch
git apply /path/to/zad-studio-operations.patch
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py migrate --plan
python manage.py migrate
python manage.py collectstatic --noinput
```

برای نصب وابستگی‌های مربوط به تصاویر HEIC، فایل `requirements-image-upload.txt` پروژه را نیز همراه با `requirements.txt` نصب کنید. کد Worker تغییر کرده است؛ انتشار آن پس از تنظیم شناسهٔ گروه سفارشی مرحله‌ای جداگانه است. تا پیش از پیکربندی گروه سفارشی، قابلیت‌های ثبت دستی و داشبورد در دسترس‌اند.

این ماژول در مسیر خصوصی `/studio/` اجرا می‌شود. دسترسی خواندن به `main.view_studioproduct` و حساب `is_staff` نیاز دارد. ثبت فلوریست، ثبت محصول و تغییر وضعیت به مجوزهای مربوط به همان مدل نیاز دارند. اکانت superuser همهٔ مجوزها را دارد.

## تغییرات پایگاه داده

مهاجرت `main.0035` مدل‌های `Florist`، `StudioProduct` و فهرست خطاهای ثبت و محدودیت‌های یکپارچگی داده را اضافه می‌کند و فیلد `studio_error` را روی پیام‌های قبلی تلگرام می‌گذارد. مهاجرت دادهٔ قبلی را حذف یا دستکاری نمی‌کند. محصولاتی که قبلاً بدون فاکتور و فلوریست ساخته شده‌اند، به طور حدسی به دفتر تولید منتقل نمی‌شوند و در «تنظیمات ← محصولات نیازمند تکمیل» دیده می‌شوند.

## ترتیب راه‌اندازی

1. از DB و media نسخهٔ پشتیبان بگیرید و کد را روی محیط آزمایشی اجرا کنید.
2. `python manage.py migrate --plan`، سپس `python manage.py migrate` و `python manage.py check` را اجرا کنید.
3. در `/studio/florists/add/` فلوریست‌ها را با کد یکتا بسازید؛ مثلاً `mz` برای مهدی و `ns` برای نیوشا. نام دقیق نیوشا را از تیم بگیرید.
4. یک گروه جدا برای سفارش‌های سفارشی بسازید، بات موجود را اضافه کنید و شناسه عددی گروه را در `TELEGRAM_STUDIO_CUSTOM_GROUP_ID` روی Django و Worker قرار دهید. `SAME_DAY_WEBHOOK_URL` و secret فعلی Worker حفظ می‌شوند.
5. Worker جدید را پس از تنظیم شناسه گروه deploy کنید. عکس و کپشن سفارشی را در گروه آزمایش کنید؛ پاسخ موفق یا خطا باید در همان گروه زیر پیام بیاید. سفارشی نباید در Same-Day سایت ظاهر شود.
6. تیم ارسال روز را با کپشن جدید آشنا کنید. در هر عکس جدید، `florist`، `type`، `factor` و `قیمت` را درج کنند. پس از تکمیل رکوردهای قبلی و تست عملی، `STUDIO_DAILY_REQUIRE_METADATA=true` را فعال کنید. تا پیش از آن، پیام‌های قدیمی هنوز در کاتالوگ کار می‌کنند اما در صورت نبود اطلاعات کامل، `StudioProduct` ناقص ساخته نمی‌شود.
7. فهرست «نیازمند تکمیل» را روزانه مرور کنید. با ویرایش کپشن پیام اصلی تلگرام، رکورد معتبر ایجاد یا به‌روز می‌شود.

## نمونه کپشن

سفارش سفارشی:

```text
florist: mz
type: box
factor: 1234
price: 2400000
```

ارسال روز (با برچسب قیمت سازگار با پارسر قبلی):

```text
florist: mz
type: box
factor: 1235
قیمت: 2400000
```

فیلدها نسبت به حروف بزرگ انگلیسی و ارقام فارسی انعطاف دارند. قیمت عدد صحیح تومان است. فاکتور در کل دفتر تولید یکتا است. یک عکس تکی لازم است؛ آلبوم پشتیبانی نمی‌شود.

## دامنه و محدودیت‌های عملیاتی

- پیام سفارشی فقط `StudioProduct` ایجاد می‌کند. فایل عکس در media ذخیره می‌شود؛ کاتالوگ عمومی هیچ رکوردی نمی‌گیرد.
- پیام ارسال روز، `Product` موجود و رکورد `StudioProduct` را با شناسه پیام تلگرام به هم وصل می‌کند. وضعیت فروش/خروج هر دو به‌روز می‌شود. عکس همان فایل محصول عمومی است و برای دفتر تولید دوباره آپلود نمی‌شود.
- تغییر مستقیم قیمت/عکس/وضعیت محصول عمومی از ادمین، اطلاعات دفتر تولید را نیز همگام می‌کند. حذف محصول عمومی سابقهٔ تولید را نگه می‌دارد و وضعیت موجود را «لغو شده» می‌کند.
- ثبت دستی از داشبورد فقط در دفتر تولید انجام می‌شود و به‌صورت خودکار محصول عمومی منتشر نمی‌کند.
- KPIها از داده‌های همین بازهٔ **تولید** حساب می‌شوند؛ «فروخته شده» یعنی محصول تولید شده در بازه که اکنون فروخته شده است. نرخ فروش برابر `sold / produced` است. نمودار تا ۳۱ روز انتهایی بازه را نشان می‌دهد. زمان فروش از `produced_at` تا `sold_at` است.
- ثبت خودکار پیام invalid رکورد ناقص نمی‌سازد. در گروه سفارشی، دلیل خطا به همان پیام پاسخ داده می‌شود. ارسال پیام وضعیت فقط روی محصول ثبت شده و در وضعیت «موجود» اثر دارد.
- پیام عکس سفارشی رد شده، در فهرست جداگانهٔ «پیام‌های سفارشی رد شده» ثبت می‌شود؛ این مورد محصول نیست. با اصلاح همان کپشن و دریافت ویرایش تلگرام، خطا خودکار بسته می‌شود. اپراتور دارای مجوز می‌تواند خطای بررسی‌شده را دستی ببندد.
