# ورودی مشترک پنل زاد

مبنای تغییر: `d86baef` (پنل فروش). ورود عمومی تیم از `/panel/` است؛ آدرس‌های
`/studio/`، `/team/`، `/sales/` و `/studio/login/` همچنان معتبرند.

## رفتار

- حساب تک‌نقشی مستقیماً وارد فضای مجاز خود می‌شود.
- حساب چندنقشی در هر ورود و هر مراجعه به `/panel/` فضای کاری را انتخاب می‌کند؛
  حتی اگر بوکمارک قبلی `next` داشته باشد.
- انتخاب با POST و CSRF در نشست همان مرورگر ذخیره می‌شود. در مراجعات بعدی
  دوباره مجوز بررسی می‌شود؛ دسترسی لغوشده از انتخاب قبلی حذف می‌شود.
  انتخاب قبلی فقط نشان داده می‌شود و باعث ورود خودکار حساب چندنقشی نیست.
- خروج از حساب انتخاب نشست را پاک می‌کند. انتخاب بین دستگاه‌ها همگام نیست.
- لینک مستقیم مجاز برای حساب تک‌نقشی و نشست معتبر حفظ می‌شود.
- نوار «تغییر فضای کاری» فقط برای حساب چندنقشی نمایش داده می‌شود.
- صفحهٔ دسترسی غیرمجاز همچنان پاسخ HTTP 403 می‌دهد؛ درخواست‌های JSON نیز
  خطا دریافت می‌کنند. انتخاب فضای کاری هیچ مجوزی ایجاد نمی‌کند.
- بوکمارک صفحهٔ اصلی یک فضای لغوشده با GET به `/panel/` برمی‌گردد؛
  نشست معتبر حفظ می‌شود. عملیات POST و صفحات عملیاتی غیرمجاز همچنان 403 دارند.
- شناسهٔ manifest قبلی ثابت است؛ نقطهٔ شروع میان‌بر به `/panel/` تغییر کرده است.
- منطق محصولات، موجودی، آمار و تلگرام در این تغییر دست‌نخورده است.

## انتشار

این تغییر migration یا نسخهٔ جدید Cloudflare Worker ندارد. مبنای سرور باید
قابلیت‌های نسخهٔ `d86baef` را داشته باشد. پس از اعمال تغییر، checks و تست‌ها،
`collectstatic` و راه‌اندازی مجدد سرویس Django لازم است.

ورودی بازهٔ دلخواه گزارش‌ها شمسی است و ارقام فارسی، عربی و انگلیسی را می‌پذیرد.
لینک‌های قدیمی با تاریخ میلادی همچنان کار می‌کنند. پیش از راه‌اندازی نسخهٔ جدید،
وابستگی `jdatetime==6.1.0` از `requirements.txt` نصب شود؛ اگر VPS دسترسی ندارد،
wheelهای این کتابخانه و `jalali-core` از سیستم محلی منتقل و آفلاین نصب شوند.

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test main.tests.test_panel main.tests.test_account_management main.tests.test_team_portal main.tests.test_sales_workspace
python manage.py collectstatic --noinput
```

## پذیرش

ورود تک‌نقشی و چندنقشی، تغییر فضای کاری بدون خروج، بازکردن مجدد `/panel/`،
لغو دسترسی انتخاب قبلی، خروج و ورود حساب دیگر و لینک غیرمجاز را بررسی کنید.
برای نسخهٔ موبایل، صفحهٔ انتخاب، نوار بالای هر سه پنل و فرم‌های باز را بررسی کنید.
جابه‌جایی مثل هر لینک ناوبری صفحهٔ جاری را ترک می‌کند؛ اطلاعات فرم باید پیش از
جابه‌جایی ثبت شوند.

## مدیریت کاربران

در مدیریت → بیشتر → مدیریت کاربران (`/studio/accounts/`) می‌توان همهٔ حساب‌ها را
جست‌وجو کرد. حساب جدید از `/studio/accounts/new/` و ویرایش از مسیر شناسهٔ کاربر
انجام می‌شود. نام، نام خانوادگی، ایمیل، نام کاربری، رمز، وضعیت ورود و ترکیب سه
دسترسی مدیر/فروش/فلوریست قابل تنظیم است. مجوز `manage_studio_accounts` لازم است؛
نقش مدیرِ ساخته‌شده با این فرم یا دستور `studio_account --manager` آن را دارد.

مدیر و فروش از مجوزها و گروه‌های عملیاتی موجود استفاده می‌کنند. دسترسی فلوریست
با اتصال حساب به پروفایل فعال اعمال می‌شود؛ پروفایل قبلی قابل انتخاب است یا
پروفایل تازه ساخته می‌شود. برداشتن دسترسی فقط اتصال حساب را باز می‌کند و پروفایل
و سابقهٔ تولید را حذف نمی‌کند. برای بازگرداندن همان کارنامه، همان پروفایل را انتخاب کنید.
مجوزهای مستقیم و گروه‌های دارای صرفاً مجوز عملیاتی هنگام ذخیره به نقش‌های انتخابی
تبدیل می‌شوند، بنابراین حذف نقش با یک مجوز مستقیم قدیمی خنثی نمی‌شود.

حساب‌های staff، superuser یا دارای مجوز فنی خارج از این سه نقش در این فرم قابل
تغییر نیستند و از Django Admin مدیریت می‌شوند. فرم اجازهٔ اعطای staff/superuser
نمی‌دهد. مدیر نمی‌تواند ورود یا نقش مدیریت خودش را حذف کند. رمز خالی در ویرایش
رمز قبلی را حفظ می‌کند؛ تغییر رمز نشست‌های قبلی دیگر را نامعتبر می‌کند.

ثبت تغییرات فرم جدید در Django LogEntry شامل مدیر، زمان، قبل/بعد و نشانگر تغییر
رمز است؛ مقدار رمز ذخیره نمی‌شود. فرم هم‌زمان قدیمی رد می‌شود. مسیر POST قدیمی
مدیریت حساب فلوریست برای سازگاری حفظ شده و محدودیت‌های قبلی خود را دارد.
